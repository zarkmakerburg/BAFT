# Stage267 — BAFT Universal Tunnel Toolbox + تحقیق رابط‌های مدرن

**مقصود محصول:** نصب BAFT و BCC باید در بلندمدت جایگزین اجرای دستی اسکریپت‌های مستقل تونل شود: کاربر موتور، جهت اتصال، سرورها، پورت‌ها، سطح امنیت و سیاست بازیابی را از BCC انتخاب می‌کند؛ Agent موتور معتبر را نصب/تنظیم و مدیریت می‌کند.

## وضعیت واقعی اکنون

- موتور قابل ساخت در این مرحله: **BAFT Secure بومی**، آن هم فقط پس از بررسی PlanHash و شروط زندهٔ هر دو نود.
- موتورهای تعریف‌شده ولی هنوز غیرقابل نصب/استقرار: **FRP، Rathole، Backhaul، WireGuard و SSH SOCKS**.
- **WSS و QUIC حامل هستند، نه موتور مستقل**؛ تا قابلیت واقعی پیاده نشود قابل انتخاب نیستند.
- صفحهٔ Toolbox، `GET /api/tunnel-engines` را با احراز هویت می‌خواند؛ سمت مرورگر نمی‌تواند یک موتور غیرفعال را فعال کند چون `RequireDeployable` نیز در ساخت واقعی fail-closed است. ادعای «نصب‌شده روی سرور» نمی‌کنیم، تا زمانی که inventory/probe امضاشدهٔ دو Agent اضافه شود.
- ارتباط ایران با خارج برای BAFT بومی IR → EX است. جهت معکوس FRP/Rathole/Backhaul بعد از آزمون واقعی مخصوص همان موتور روشن می‌شود. انتخاب جهت در PR #234 است و انتخاب/تولید پورت مقصد Xray در PR #231.
- **نه پنل سنایی را مخفیانه تغییر می‌دهیم، نه ورودی عمومی ایران را بی‌سروصدا راه می‌اندازیم.** کاربر باید جریان واقعی ورودی و مقصد را تأیید کند.

## طراحی نهایی مورد نظر — ادغام، نه جایگزینی

- BCC کلاسیک با فرم‌ها، سوابق و کنترل‌های موجود حفظ می‌شود؛ **Aurora** همان هویت طراحی اصلی را به‌صورت لایهٔ مشترک می‌آورد.
- UX اصلی: خانهٔ ابزارها (موتور + قابلیت + وضعیت) → Wizard مبتنی بر نقش و نوع مسیر → پیکربندی/پورت مقصد → مرور PlanHash → اجرا → پایش و اصلاح.
- طراحی: **FA/EN + RTL/LTR + Light/Dark**، کارت‌های کم‌تراکم با typography حرفه‌ای، micro-interaction ملایم و حالت reduced motion، mobile-first، بدون شلوغی بصری.
- Health و Telemetry فقط از دادهٔ واقعی و تازه نشان داده می‌شوند؛ نبود شواهد = UNKNOWN، نه وضعیت سبز.
- مدیر عملیات: Alert → Incident Center → Diagnose → Plan → Apply → Verify → Rollback، با permission و audit trail.

## گام‌های اجرایی و گیت پذیرش

**P0:** API احراز‌هویت‌شدهٔ موتورهای واقعی، capability manifest از backend، کارت‌های فعال/غیرفعال، قرارداد driver (#228)، راه‌اندازی امن نخست FRP (#229) و سپس Rathole (#230)، بستهٔ امضاشده/پین‌شده، cleanup/rollback و دو نود E2E. هر موتور باید مستقل از نمونه‌ها و تونل‌های خواهر بماند. ثبت مجوز و provenance برای باینری خارجی الزامی.

**P1:** مدیریت چند پورت ورودی/مقصد (port mapping) واقعی، preflight تعارض پورت و جهت، نصب و به‌روزرسانی امن موتور، backup/restore، ویرایش/حذف/توقف/شروع سرویس، لاگ؛ Library widgets و Node Inspector و Network Map واقعی.

**P2:** جست‌وجوی فرمان و میان‌برهای صفحه، نقش‌بندی اپراتور، تم‌ها/چیدمان‌های سفارشی، هشدارهای هوشمند قابل توضیح، ابزار مهاجرت و import از اسکریپت‌های شناخته‌شده با تأیید و مالکیت.

**پذیرش Stage267:** بدون توکن امکان دریافت کاتالوگ وجود ندارد؛ درخواست غیر GET مردود است؛ در backend تمام موتورهای برنامه‌ریزی‌شده fail-closed هستند؛ در UI فقط BAFT به Wizard راه دارد و شکست API تمام کارت‌های اقدام را غیرفعال می‌کند. ادغام و release فقط پس از CI و مجوزهای انتشار.
