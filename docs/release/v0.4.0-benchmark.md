# v0.4.0 tunnel data-path benchmark (v0.3.7 vs claude/v040-integration @ 7593900)

Scope: regression check only. No product code was changed. Harness files added
by this branch (`claude/v040-bench`):

- `internal/benchpath/session_bench_test.go` - compiles unchanged against BOTH
  revisions (session pair over a loopback TCP carrier, echo target).
- `internal/benchpath/session_idle_bench_test.go` - v0.4.0 only
  (`FlowIdleTimeout` enabled).
- `internal/publicingress/forwarder_bench_test.go` - v0.4.0 only
  (`internal/publicingress` does not exist in v0.3.7).

No pre-existing benchmark covered these paths (only `bcc.SaveWithLargeLedger`,
`protocol.Encode32K`, `recordshape.Morphing` exist; the `bench/stage-e*` branches
hold a scenario runner that wraps tests, not Go benchmarks of the session path).

## What changed on the data path (v0.3.7..7593900)

`git diff --stat` over `internal/carrier`, `scheduler`, `resources`, `recovery`,
`routes`: no non-test change. `internal/protocol`: only
`handshake.go` capability validation (handshake time, not per frame). The
data-path deltas are: `session.go` (one extra `tuneAppConn` call plus
`newIdleConn` wrapper per Flow open; idle wrapper is a no-op unless
`FlowIdleTimeout > 0`), new `idle_conn.go`, node fallback logic (control plane),
and the new `internal/publicingress` forwarder. Consequently `h2`/`ws`/Noise
carriers are byte-identical between the releases; a carrier benchmark would
measure the same code twice and was not written. The session benchmarks use a
raw loopback TCP carrier to isolate `internal/session`.

## Method

- 4 vCPU Intel Xeon @ 2.10 GHz sandbox VM, Go 1.27.x, loopback only, no netem.
- Session: two test binaries built once, run INTERLEAVED (037, 040, 037, ...)
  for 16 rounds, default 1 s `-benchtime`, `-benchmem`. benchstat (x/perf) with
  16 samples per side. An earlier 8-round run taken while the host was loaded by
  other jobs (load average 12-16 on 4 vCPU, +/-20-55 % spread) gave the same
  "no change" verdict; the table below is the quiet-host run (load 2-3).
- Publicingress: one revision only. Each scenario is run against three fronts
  with the same backend and client: `direct` (no proxy), `naive` (accept, dial,
  two `io.Copy`, no peek) and `forward` (v0.4.0 `forward()` driven from a bare
  accept loop, as `probe_test.go` does, because `Serve` fails closed without
  `/proc/net/tcp6`). 8 rounds, fixed iteration counts (400x fast, 60x for the
  ~50 ms scenarios). Host load < 1.
- Reported values are benchstat centers with its +/- spread (95% CI of the
  median); "~" means p >= 0.05 (no detectable difference).

| Ping-pong 64 B (sec/op) | 137.0 us +/-5% | 135.0 us +/-8% | 0.99 (p=0.12) | no measurable change |
| Ping-pong 32 KiB (sec/op) | 212.3 us +/-4% | 219.6 us +/-7% | 1.03 (p=0.59) | no measurable change |
| Stream echo 256 KiB (sec/op) | 889.3 us +/-12% | 895.6 us +/-10% | 1.01 (p=0.84) | no measurable change |
| B/op, all four | 209.0 KiB / 2.854 KiB / 67.53 KiB / 545.0 KiB | 209.0 / 2.852 / 67.53 / 546.2 KiB | 1.00 | no change |
| allocs/op, all four | 224 / 36 / 34 / 277 | 224 / 36 / 34 / 276 | 1.00 | no change |

v0.4.0 with `FlowIdleTimeout=300s` (idle wrapper enabled; not the default
unless `limits.flow_idle_seconds` is set): open 606 us, 64 B 132 us, 32 KiB
221 us, stream 836 us - all within noise of the disabled case. Allocations:
+8 allocs/op (+0.6 KiB) per Flow open, 0 on the steady-state read/write path.

Throughput equivalent of the stream benchmark: ~280 MiB/s both releases (single
flow, loopback, CPU-bound on 4 shared vCPU).

## (a) Public ingress forwarder (new in v0.4.0; no v0.3.7 counterpart)

Connect to first response byte, medians, n=8:

| scenario | direct | naive proxy (no peek) | v0.4.0 forward() | forward vs naive |
|---|---|---|---|---|
| client speaks first (write 1 B, read echo) | 122.8 us +/-22% | 195.8 us +/-15% | 236.1 us +/-21% | +20.6% (+40 us, p=0.015) |
| silent client, server banner first | 96.7 us +/-17% | 167.4 us +/-23% | 50.89 ms +/-0% | +50.7 ms (peek window, by design) |
| valid probe prefix then data (`BAFT-`) | 130.4 us +/-16% | 208.7 us +/-21% | 50.93 ms +/-0% | +50.7 ms (full peek window) |
| established, 64 B ping-pong | 8.5 us +/-36% | 16.7 us +/-41% | 21.2 us +/-22% | ~ (p=0.13) |
| established, 256 KiB streaming | 767 MiB/s +/-12% | 842 MiB/s +/-10% | 565 MiB/s +/-16% | -32.9% (p<0.001) |

Allocation (process-wide, includes proxy goroutines): forward = 72-73 allocs and
~67.7 KiB per accepted connection vs 58-59 allocs / 3.3 KiB for the naive proxy;
steady-state streaming 0 allocs/op for all fronts.

The probe responder path (exact probe frame, echo, rate limited to 5 per source
per second) was not benchmarked: it never dials the target, so it is cheaper than
any forwarded connection, and the per-source limiter would reject repeated
loopback probes after the burst.

## Verdicts

| metric | verdict |
|---|---|
| Session OpenFlow latency, 64 B / 32 KiB latency, 256 KiB stream throughput, B/op, allocs/op (v0.3.7 -> v0.4.0) | no measurable change (all p > 0.05, ratios 0.99-1.03, within noise) |
| Idle-wrapper cost (enabled) | no measurable change in time; +8 allocs per Flow open |
| h2 / ws / Noise carrier | not benchmarked: source byte-identical between releases |
| Connect latency, client speaks first | forwarder adds ~40 us (about +20%) over a bare dial+copy proxy and ~110 us over a direct dial; negligible against any WAN RTT. No v0.3.7 baseline exists (new component) |
| Connect latency, client silent / server-speaks-first (SSH, SMTP style) | **+50 ms per connection**, deterministic (peek window), not noise. This is the documented design (`probePeekWindow`), not a bug; it is the only user-visible latency regression and it applies to server-first protocols only. A client whose first bytes are a valid probe-prefix but never complete the frame pays the same 50 ms |
| Forwarder passthrough throughput | not a regression vs v0.3.7 (no baseline); versus a naive io.Copy proxy it is ~33% lower (565 vs 842 MiB/s on loopback) |

Likely cause of the 33% (from reading `forward()`, not separately verified):
`activityReader` wraps each source, so `io.Copy` cannot use the TCPConn
`WriteTo`/`ReadFrom` splice fast path and falls back to 32 KiB user-space
copies (this also explains ~64 KiB per connection of copy buffers). On loopback
with fast peers this is visible; on a real WAN path the tunnel session, not the
forwarder, is the bottleneck (session streaming here is ~280 MiB/s, below the
forwarder's ~565 MiB/s). Not tuned, per task scope.

No regression above 10% outside noise was found between v0.3.7 and v0.4.0 in the
code both revisions share, so no bisect was needed.

## Caveats

- Shared sandbox VM, 4 vCPU; other jobs raised load average to 12-16 during the
  first session run. Use ratios and the quiet-run p-values, not absolute us.
- Loopback only: no RTT, no TLS/Noise, no netem. Absolute throughput numbers
  are CPU-bound artifacts and not link speeds.
- Session numbers use a TCP carrier (not h2/ws) because those packages are
  unchanged; end-to-end node-level numbers (config, Noise, TLS) were not taken.
- `Serve()` (live-port inventory via /proc/net/tcp6) not exercised; `forward()`
  is the same per-connection code. No GitHub Actions workflow was needed.
- Publicingress has no v0.3.7 baseline; "naive" and "direct" are same-harness
  stand-ins, not a historical comparison.

    git worktree add ../bench-v037 v0.3.7

    go test -c -o bp037.test ../bench-v037/internal/benchpath   # run from that tree

    # alternate runs of both binaries, then:
    benchstat t037.txt t040.txt
    go test -run '^$' -bench . -benchmem -benchtime=400x ./internal/publicingress
