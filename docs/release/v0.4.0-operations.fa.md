# راهنمای عملیاتی v0.4.0

[English](v0.4.0-operations.md)

این صفحه کارهایی را شرح می‌دهد که اپراتور برای نصب، pair، اجرا، به‌روزرسانی، پشتیبان‌گیری و بازیابی یک استقرار v0.4.0 انجام می‌دهد. مراحل روزمره در راهنمای کاربر آمده‌اند ([فارسی](../fa/guide/README.md)، [English](../en/guide/README.md)). این صفحه فقط چیزهایی را پوشش می‌دهد که v0.4.0 اضافه یا عوض کرده و به صفحه‌های جزئی‌تر ارجاع می‌دهد. محدودیت‌ها در [KNOWN-LIMITATIONS.md](../../KNOWN-LIMITATIONS.md) آمده‌اند.

## ۱. نصب و pair

مانند راهنما: [نصب](../fa/guide/01-install.md).

<div dir="ltr" align="left">

```bash
sudo bash install.sh --role ex --public-address HOST_OR_IP
sudo bash install.sh --role ir --pairing-code BAFTPAIR1:...
sudo bash install.sh --plan            # inspect, change nothing
```

</div>

تازه در v0.4.0:

- نصب‌کننده سرویس `baft-recover.service` را هم نصب می‌کند. این سرویس هنگام بوت یک بار `baft recover boot` را اجرا می‌کند تا تغییرات tunnel را که با crash یا قطع برق نیمه‌کاره مانده‌اند تمام کند یا برگرداند. پس از فایل‌سیستم‌های محلی اجرا می‌شود و هرگز pair نمی‌کند، کلید عوض نمی‌کند و به فایل‌های غریبه دست نمی‌زند.
- گزینه‌ی `--agent-only` (سرورهای مدیریت‌شده با BCC) زنجیره‌ی خالی و ثابت `inet baft ingress` را در nftables می‌سازد. اگر چیدمان دیگری از قبل وجود داشته باشد، رد می‌شود و به اشیای nft غریبه دست زده نمی‌شود. `--no-ingress-chain` این مرحله را رد می‌کند. `--provision-ingress-policy` هم bootstrap محلیِ سیاست را (فقط با root) اجرا می‌کند؛ پیش‌فرض خاموش است و به‌تنهایی public ingress را فعال نمی‌کند.

## ۲. چند IR روی یک listener در EX (multiplex مشترک)

یک listener، پورت و پروسه‌ی EX می‌تواند به چند IR (tenant) با هویت و مقصد جداگانه سرویس بدهد، بدون اینکه جریان‌های زنده قطع شوند:

<div dir="ltr" align="left">

```bash
baft-pair ex-accept ... --join /etc/baft/baft.yaml   # add this IR as a tenant
systemctl reload baft                                 # SIGHUP: apply live
```

</div>

`limits.max_flows_per_peer` سقف تعداد جریان‌های هر tenant را تعیین می‌کند. طراحی و کمبودهای فعلی: [shared-multiplexing.md](../design/shared-multiplexing.md). ساخت instance با listener مشترک هنوز از مسیر تراکنش tunnel و instance سیستم‌دی پیاده نشده و مسیر پشتیبانی‌شده همان `--join` است.

## ۳. Public ingress (مدیریت‌شده با BCC)

Public ingress **به‌طور پیش‌فرض بسته** است. BCC کار امضاشده‌ی Apply یا Retire را فقط برای نودی در صف می‌گذارد که enroll شده و agent آن heartbeat تازه با capability `operational-ingress-v1` فرستاده باشد. نود کار را فقط با امضای تأییدشده، lease نگه‌داشته‌شده و pin سیاست نصب‌شده می‌پذیرد. Wizard کارت config را فقط پس از رسید احراز هویت‌شده و یک probe مستقل از پورت عمومی نشان می‌دهد.

پس از restart شدن agent:

<div dir="ltr" align="left">

```bash
baft-agent --ingress-reconcile auto     # default: finish only with full evidence
baft-agent --ingress-reconcile report   # evaluate and print, change nothing
baft-agent --reconcile-ingress          # one-shot: print evidence and exit
```

</div>

حالت `auto` فقط چیزی را حذف می‌کند که شواهد کرنل، فایروال و authority ثابت کنند متعلق به خود ماست. هر چیز نامطمئن fence شده باقی می‌ماند و گزارش می‌شود.

## ۴. به‌روزرسانی

سرورها: نصب‌کننده را دوباره اجرا کنید (ضد downgrade، اول plan، بازگشت خودکار): [به‌روزرسانی، پشتیبان و حذف](../fa/guide/05-update-backup-uninstall.md).

مرکز به‌روزرسانی BCC ([طراحی](../design/update-center.md)):

- یک release امضاشده را که با `scripts/release/update_center_bundle.sh <unpacked offline bundle>` ساخته شده import کنید.
- plan هر نود را بازبینی کنید و با تأیید تایپی `UPDATE <node> <version>` اعمال کنید. ارتقا از کار امضاشده‌ی موجود `update_baft` استفاده می‌کند و بازگشت همیشه با نصب‌کننده‌ی تأییدشده روی خود نود انجام می‌شود.
- import با کلید ریشه‌ی release پین‌شده (`--update-root-pub`) تأیید می‌شود. `install.sh` همان کلید ریشه‌ای را که نصب با آن تأیید شده در فایل `release-root.pub` در پوشه‌ی پیکربندی BCC می‌نویسد و به سرویس BCC می‌دهد. اجرای دوباره آن را عوض نمی‌کند، مگر اینکه کلید ریشه‌ی دیگری داده شود. دریافت از آینه پیاده نشده و import دستی است.

## ۵. پشتیبان‌گیری و بازیابی

BCC: [پشتیبان‌ها و بازیابی](../en/29-bcc-backup-restore-preview.md).

<div dir="ltr" align="left">

```bash
baft-bcc restore-preview --backup FILE --state-file STATE   # read-only
baft-bcc restore --backup FILE --state-file STATE --yes     # BCC stopped
```

</div>

پشتیبان‌گیری رمزشده‌ی زمان‌بندی‌شده به کلید پشتیبان نیاز دارد (`--backup-key-file` که ترجیح دارد، یا `BAFT_BCC_BACKUP_KEY`). `install.sh` یک کلید که فقط root به آن دسترسی دارد، به نام `backup-key` در پوشه‌ی پیکربندی BCC می‌سازد و به سرویس BCC می‌دهد. اجرای دوباره آن را عوض نمی‌کند. بدون این کلید پشتیبان‌ها خوانده نمی‌شوند، پس یک نسخه از آن را جایی امن و دور از خود پشتیبان‌ها نگه دارید.

سرورها: `/etc/baft` پیکربندی، کلیدها و گواهی‌ها را نگه می‌دارد و حذف استاندارد آن را حفظ می‌کند. نصب‌کننده فایل‌هایی را که عوض می‌کند در `/opt/baft/backups/rerun-<time>/` کپی می‌کند.

## ۷. ارتقا از v0.3.7

یک بار pair کنید و بعد نصب‌کننده را روی هر دو طرف دوباره اجرا کنید. peerهای v0.3.7 کار می‌کنند: تبادل capability در HELLO به فرمت wire ثابت‌شده‌ی v0.3.7 برمی‌گردد، و دو گردش‌کار LAB برای v0.3.7 (`gamma-v037-upgrade-lab` و `gamma-v037-tunnel-upgrade-lab`) جایگزینی باینری بدون pair دوباره را پوشش می‌دهند. قواعد downgrade پایگاه داده و پشتیبان‌های BCC در [KNOWN-LIMITATIONS.md](../../KNOWN-LIMITATIONS.md) آمده‌اند.
