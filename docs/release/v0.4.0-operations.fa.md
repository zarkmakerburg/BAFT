## ۱. نصب

نصب‌کننده نسخهٔ امضاشدهٔ مناسب معماری را دانلود می‌کند، آن را با کلید ریشهٔ پین‌شده و فهرست ابطال وارسی می‌کند و بازگشت به نسخهٔ قدیمی‌تر یا نسخهٔ دوباره‌برچسب‌خورده را رد می‌کند. اول `--plan` را اجرا کنید: چیزی را تغییر نمی‌دهد و نه root می‌خواهد و نه شبکه.

<div dir="ltr" align="left">

```sh
curl -fsSLO https://raw.githubusercontent.com/zarkmakerburg/baft/main/install.sh
sudo bash install.sh --plan
```

</div>

(پیوست‌های انتشار، نصب‌کننده را با نام `baft-install-linux-<arch>` هم دارند که بایت‌به‌بایت با `install.sh` یکی است؛ BCC همین فایل را از راه SSH روی سرورهای جدید می‌فرستد.)

**مرکز فرمان (BCC)، لایهٔ کنترل** (هرگز تونل نمی‌سازد):

<div dir="ltr" align="left">

```sh
sudo bash install.sh --bcc-only
sudo bash install.sh --bcc-only --bcc-domain panel.example.com --bcc-port 8443
```

</div>

بدون `--bcc-domain` پنل روی `127.0.0.1:8080` گوش می‌دهد و از راه تونل SSH یا یک reverse proxy که خودتان می‌گذارید باز می‌شود. نصب‌کننده مسیر مخفی داشبورد و گذرواژهٔ یک‌بارمصرف را فقط یک بار چاپ می‌کند؛ اجرای دوباره `password: not stored` می‌نویسد. با `sudo baft-panel` ورود تازه بسازید. توکن مدیر `/etc/baft-bcc/admin-token` است (root، حالت 0600) و برای API زیر به کار می‌رود. برای ثبت سرورهای جدید با SSH از پنل، BCC به `--bcc-public-url https://...` نیاز دارد (`http://` فقط همراه `--bcc-allow-insecure-http`).

**سرور تحت مدیریت BCC (agent)**: توکن عامل از `BAFT_AGENT_TOKEN_FILE` و کلید عمومی امضای کارهای BCC از `BAFT_BCC_JOB_KEY` می‌آید (روی میزبان BCC: `baft-bcc jobkey show --job-key-file /etc/baft-bcc/job-key`):

<div dir="ltr" align="left">

```sh
sudo env BAFT_AGENT_TOKEN_FILE=/root/agent.token BAFT_BCC_JOB_KEY=PUBLIC_KEY \
  bash install.sh --agent-only --bcc-url https://bcc.example.com --node-id ir-1
```

</div>

`--agent-only` زنجیرهٔ خالی nftables با نام `inet baft ingress` را هم می‌سازد (بخش ۳)؛ برای رد کردن آن `--no-ingress-chain` را بدهید. میزبان‌های آفلاین: `--offline DIR` با `baft-offline-<version>.tar.gz` باز‌شده.

## ۲. جفت‌سازی

### با BCC

سرور را در پنل اضافه کنید (ثبت با SSH، یا نصب agent بالا) و تونل را در Smart Tunnel Wizard بسازید. BCC برنامهٔ بازبینی‌شده را با **plan hash** نشان می‌دهد؛ تونل فقط از همان hash ساخته می‌شود و گره‌ها آن را به‌صورت کار امضاشده و با بازگشت‌پذیری اعمال می‌کنند. هیچ‌چیز بدون امضا به گره نمی‌رسد.

### CLI مستقل (وقتی BCC در دسترس نیست)

دو راه، هر دو بدون BCC:

۱. جفت‌سازی کلاسیک با نصب‌کننده. روی سرور بیرون (EX):

<div dir="ltr" align="left">

```sh
   sudo bash install.sh --role ex --public-address EX_IP --ports 443,2053
```

</div>

   یک کد یک‌بارمصرف `BAFTPAIR1:` چاپ می‌کند (۱۵ دقیقه اعتبار، فقط یک بار). روی سرور ایران (IR):

<div dir="ltr" align="left">

```sh
   sudo bash install.sh --role ir --pairing-code 'BAFTPAIR1:...'
```

</div>

   کد پاسخ `BAFTREPLY1:` را روی EX برگردانید (یا با `--reply-code` بدهید). با `--ir-ssh USER@HOST` خود EX، IR را نصب و جفت می‌کند. `--re-pair` عمداً جفت‌سازی تازه شروع می‌کند؛ اجرای دوباره هرگز خودش دوباره جفت نمی‌کند.

۲. جفت‌سازی در محدودهٔ یک instance با `baft tunnel` (همان چیزی که agent صدا می‌زند). هر فراخوانی `--instance`، `--metrics-listen` و `--id` می‌خواهد:

<div dir="ltr" align="left">

```sh
   baft tunnel ex-code --instance main --metrics-listen 127.0.0.1:9291 --id t1 \
     --address EX_IP --port 443 --target 127.0.0.1:2443 --route-id r1 --output-file /root/ex.code
   baft tunnel ir-apply --instance main --metrics-listen 127.0.0.1:9292 --id t1 \
     --code-file /root/ex.code --route-listen 127.0.0.1:1443 --route-id r1 --output-file /root/ir.reply
   baft tunnel ex-accept --instance main --metrics-listen 127.0.0.1:9291 --id t1 --reply-file /root/ir.reply
   baft tunnel ir-start --instance main --metrics-listen 127.0.0.1:9292 --id t1
   baft tunnel health --instance main --metrics-listen 127.0.0.1:9291 --id t1
```

</div>

   (`ir-apply` روی IR اجرا می‌شود و کد EX در فایل خصوصی ۰۶۰۰ کپی شده است؛ `rollback` و `finalize` چرخهٔ عمر را کامل می‌کنند.) کدها و پاسخ‌ها راز هستند: از فایل‌های ۰۶۰۰ استفاده کنید، نه خط فرمان. کد یا پاسخ ناقص، دستکاری‌شده، منقضی، تکراری یا نامتناظر رد می‌شود و وضعیت در انتظار برای تلاش دوباره می‌ماند.

## ۳. ingress عمومی عملیاتی

ingress عمومی یک پورت TCP روی میزبان IR باز می‌کند و آن را به مسیر تونل می‌فرستد. **پیش‌فرض بسته است**: مگر همهٔ شرط‌های زیر برقرار باشند چیزی باز نمی‌شود.

روی گرهٔ IR، agent مجری عملیاتی را فقط وقتی می‌سازد که همه برقرار باشند؛ وگرنه قابلیتی اعلام نمی‌کند و کارهای ingress در وضعیت BLOCKED می‌مانند:

- سیاست گرهٔ مدیریت‌شدهٔ نصب‌شده، `/etc/baft/ingress/managed-node.json`، برای همین `--node-id` بارگذاری شود؛
- `<state-dir>/ingress-authority` و `<state-dir>/ingress-journal` خصوصی (۰۷۰۰) باشند و زنجیرهٔ journal معتبر باشد؛
- `/usr/sbin/nft` (یا `/sbin/nft`) دقیقاً یک زنجیرهٔ `inet baft ingress` (`type filter hook input priority -100; policy accept`) با handle پایدار گزارش کند. agent هرگز زنجیره را نمی‌سازد: `install.sh --agent-only` این کار را بی‌اثر در اجرای دوباره انجام می‌دهد و اگر زنجیره‌ای با همین نام و چیدمان دیگر باشد رد می‌کند (کد خروج ۳، بدون تغییر).

**پرچم راه‌اندازی سیاست.** سیاست محافظت‌شده فقط به درخواست ساخته می‌شود، هرگز ضمنی نیست:

<div dir="ltr" align="left">

```sh
sudo bash install.sh --agent-only --bcc-url https://bcc.example.com --node-id ir-1 --provision-ingress-policy
sudo baft-agent --provision-ingress-policy --node-id ir-1
```

</div>

این فرمان محلی و فقط‌root است: بدون تماس با BCC، بدون پورت، بدون قاعدهٔ فایروال، بدون Apply.

**جریان کار.** در Wizard برنامهٔ بازبینی‌شده گره‌ها، مقصد، نوع انتقال، generation، plan hash و `ConfigPort == Port` را می‌بندد (پورت داخل پیکربندی کلاینت برابر پورت عمومی واقعی است). BCC یک Apply امضاشده به agent ثبت‌نام‌شدهٔ عادی می‌فرستد. agent فقط زیر یک lease نگه‌داشته‌شده و به‌صورت محلی وارسی‌شده شنوندهٔ پورت و قاعدهٔ nftables را باز می‌کند، سپس رسید HTTPS احراز‌هویت‌شده می‌فرستد (agent به BCC، با اعتبارسنجی گواهی، بدون تنزل). BCC خودش هم پورت را می‌آزماید.

**«Ready» یعنی چه.** `GET /api/ingress/readiness?tunnel_id=ID` (با توکن مدیر) `{verified, ready, reason, card}` برمی‌گرداند. فقط وقتی `Ready` است که همه برقرار باشند: Apply ارسال شده؛ رسید دقیق و احراز‌هویت‌شدهٔ *applied* با مالکیت وارسی‌شده و شواهد کامل شنونده/فایروال هست؛ و یک مشاهدهٔ تازهٔ BCC (حداکثر ۵ دقیقه) دربارهٔ binding، هویت socket، handleهای chain و rule در nft و یک رفت‌وبرگشت بار TCP با رسید موافق است. آمادگی در لحظه محاسبه می‌شود و هرگز ذخیره نمی‌شود، پس پشتیبانِ بازیابی‌شده یا رکورد کهنه نمی‌تواند آن را حمل کند؛ Retire آن را خاموش می‌کند. کارت پیکربندی قابل‌استقرار کلاینت (`tunnel_id`، `ir_node`، `config_port`، `public_port`، `plan_sha256`) فقط در همین حالت نشان داده می‌شود و رازی ندارد.

<div dir="ltr" align="left">

```sh
curl -fsS -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" \
  "http://127.0.0.1:8080/api/ingress/readiness?tunnel_id=TUNNEL_ID"
```

</div>

**مدل اعتماد (پیش از تکیه بر Ready بخوانید).** به خطر افتادن agent گره خارج از دامنه است. مشاهدهٔ BCC از شواهد خود agent استفاده می‌کند، پس تنها دادهٔ مستقل یک نشانهٔ echo است که هر فرایندِ نگه‌دارندهٔ پورت می‌تواند بسازد. بنابراین Ready یعنی «عملیات امضاشده کامل شد و BCC توانست از پورت عبور کند»، نه «BAFT ثابت‌شده مالک شنونده است» و نه «از اینترنت عمومی در دسترس است»: نتایج LAB روی loopback و namespace دسترس‌پذیری بیرونی را تأیید نمی‌کنند. پیش از دادن پیکربندی، از بیرون آزمایش کنید.

**دروازهٔ انتشار.** گردش‌کار `operational ingress v1` باید روی SHA تگ با صفر تست رد‌شدهٔ الزامی بگذرد؛ وگرنه `accept.sh` تگ را نمی‌پذیرد. به [دروازه](v0.4.0-gate.md) نگاه کنید.

## ۴. به‌روزرسانی و بازگشت

به‌روزرسانی همان اجرای دوبارهٔ نصب‌کنندهٔ وارسی‌شده است؛ مرکز به‌روزرسانی داخل محصول وجود ندارد. اجرای دوباره میزبان را بررسی می‌کند، برنامه را چاپ می‌کند، فقط همان را اعمال می‌کند، نتیجه را وارسی می‌کند و اگر وارسی رد شود فایل‌ها و وضعیت سرویس قبلی را برمی‌گرداند. هرگز کلید را عوض نمی‌کند، پیکربندی معتبر را بازنویسی نمی‌کند و دوباره جفت نمی‌کند.

<div dir="ltr" align="left">

```sh
sudo bash install.sh --plan --json
sudo bash install.sh --role ex --public-address EX_IP --yes
sudo bash install.sh --bcc-only --yes
sudo bash install.sh --version vX.Y.Z --yes
```

</div>

ترتیب: اول BCC، بعد سرورها، یکی‌یکی، و بین مرحله‌ها `baft doctor` و ترافیک را بررسی کنید. BCC می‌تواند کارهای امضاشدهٔ به‌روزرسانی را هم به agentهای ثبت‌شده بفرستد: `POST /api/deploy` با `{"node_ids":["ir-1"],"version":"vX.Y.Z"}`.

- نسخهٔ قدیمی‌تر از نصب‌شده رد می‌شود مگر `--allow-downgrade` بدهید.
- نسخه‌ای که باینری‌اش بالا نمی‌آید یا به‌عنوان سرویس می‌میرد خودکار برگردانده می‌شود.
- پیش از هر تغییر، نصب‌کننده هر فایلی را که لمس می‌کند در `/opt/baft/backups/rerun-<time>/` کپی می‌کند (سه مورد آخر نگه داشته می‌شود).
- بازگشت به نسخهٔ قدیمی‌تر از **SQLite schema 15/16 یا backup schema 4/5 به snapshot وارسی‌شدهٔ پیش از ارتقا نیاز دارد** (بخش ۶): `baft-bcc` نسخهٔ v0.3.7 وضعیت v0.4.0 را رد می‌کند («newer than this build supports») و پشتیبان v0.4.0 را هم («unsupported backup schema version»).

## ۴ب. مرکز به‌روزرسانی (BCC)

BCC هرگز خودش چیزی را به‌روز نمی‌کند. اپراتور یک بستهٔ انتشار امضاشده را وارد می‌کند، BCC آن را با ریشهٔ انتشار پین‌شده وارسی می‌کند (فهرست ابطال، کف نسخه، بررسی re-tag)، نسخهٔ نصب‌شده در برابر آخرین را برای هر سرور نشان می‌دهد و مدیر یک برنامهٔ وابسته به hash را روی **یک** سرور اعمال می‌کند که کار امضاشدهٔ موجود `update_baft` را صف می‌کند. ورودی‌ها پایدارند (SQLite schema 16 و backup schema 5) و بازیابی هرگز ورودی‌ای را فراموش نمی‌کند و فهرست ابطال قدیمی‌تر را زنده نمی‌کند.

**پین ریشهٔ انتشار.** BCC فایلی با کلید عمومی ریشهٔ انتشار لازم دارد که با `--update-root-pub` داده می‌شود (پیش‌فرض آن `--component-catalog-root` است). `install.sh` امروز این پرچم را به `baft-bcc` **نمی‌دهد**، هرچند همان کلید ریشه داخل `install.sh` پین شده است (`BAFT_PINNED_ROOT_PUB`)؛ تا آن زمان آن را با drop-in اضافه کنید (`systemctl edit baft-bcc`، همان بازنشانی `ExecStart=` بخش ۵، با افزودن `--update-root-pub /etc/baft-bcc/release-root.pub`) و فایل را بنویسید:

<div dir="ltr" align="left">

```sh
printf '%s\n' 'NJq0LmZ503x67pdXSuNGmSOqaiNJDpYf9nDE8Bwa-JI' > /etc/baft-bcc/release-root.pub
```

</div>

بدون پین، `POST /api/updates/import` پاسخ ۵۰۳ می‌دهد و چیزی وارد نمی‌شود. سپس:

<div dir="ltr" align="left">

```sh
scripts/release/update_center_bundle.sh /path/to/unpacked-baft-offline-vX.Y.Z > update-bundle.json
curl -fsS -X POST -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" --data-binary @update-bundle.json \
  http://127.0.0.1:8080/api/updates/import
curl -fsS -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" http://127.0.0.1:8080/api/updates
```

</div>

`POST /api/updates/plan` (با `node_id`، `kind` برابر `upgrade` یا `rollback` و `target_digest`) برنامه را با `plan_hash` و متن دقیق تأیید برمی‌گرداند؛ `POST /api/updates/apply` همان فیلدها به‌علاوهٔ `plan_hash` و `confirmation` می‌خواهد. وارد کردن برای rollback علاوه بر آن سرآیند `X-BAFT-Downgrade-Confirmation: DOWNGRADE <version> <commit>` را می‌خواهد. گزینهٔ Update در منوی `baft` فقط راهنمای خواندنی است.

## ۴پ. مذاکرهٔ قابلیت‌ها و بازیابی هنگام بوت

**مذاکرهٔ قابلیت‌ها (مجموعهٔ v1).** `HELLO`/`HELLO_ACK` قابلیت‌های `carrier.h2`، `carrier.ws`، `noise.v1` و `shape.v1` را می‌برند؛ هر طرف آنچه پیکربندی‌اش فعال کرده اعلام می‌کند، session اشتراک را به کار می‌برد و نبود قابلیت الزامی با دلیل تایپ‌دار رد می‌شود (بدون تنزل بی‌صدا). در هر دو جهت با v0.3.7 سازگار است. کلید اختیاری `transport.require_capabilities` باعث می‌شود همتایی که قابلیتی از فهرست را ندارد، **از جمله همتای v0.3.7**، رد شود؛ در ارتقای تدریجی آن را روی هر دو گره خالی بگذارید و فقط پس از آنکه همهٔ گره‌ها v0.4.0 شدند تنظیم کنید (تحلیل‌گر پیکربندی v0.3.7 کلید ناشناخته را رد می‌کند). به `docs/en/04-protocol-baft1.md` نگاه کنید.

**بازیابی هنگام بوت.** `baft-recover.service` (نصب‌کننده نصب و فعالش می‌کند؛ پیش از `sysinit.target`، `baft.service` و agent مرتب شده و فقط ترتیب می‌دهد، هرگز نیازمندی نیست) فرمان `baft recover boot` را اجرا می‌کند که تغییر ناتمام تونل را از شواهد روی دیسک آشتی می‌دهد و هرگز سرویسی را شروع، متوقف یا راه‌اندازی مجدد نمی‌کند. برای بررسی دستی:

<div dir="ltr" align="left">

```sh
baft recover boot --json
```

</div>

بازیابی ناموفق یا قفل‌شده در `systemctl --failed` دیده می‌شود و بوت را هرگز مسدود نمی‌کند.

## ۵. پشتیبان‌گیری و بازیابی

وضعیت BCC (گره‌ها، هش توکن ثبت‌نام، ورودی‌های مرکز به‌روزرسانی، تونل‌ها و plan hashها، jobها، رزروها، مالی، زنجیرهٔ هش audit) به‌صورت فایل رمزنگاری‌شده (AES-GCM، سرآیند احراز‌هویت‌شده، backup schema 5) پشتیبان گرفته می‌شود. **در پشتیبان نیست**: کلید امضای کارها (agentها آن را پین می‌کنند)، توکن مدیر، فایل دسترسی، فایل‌های TLS و خود کلید پشتیبان. آن‌ها را جداگانه امانت نگه دارید.

**فعال‌سازی.** نصب‌کننده کلید پشتیبان نمی‌نویسد. یک فایل کلید خصوصی و یک drop-in برای systemd بسازید (فایل کلید باید فایل معمولی، مالک = کاربر سرویس، حالت ۰۶۰۰، یک لینک و بدون symlink باشد؛ `--backup-key-file` بر متغیر محیطی `BAFT_BCC_BACKUP_KEY` برتری دارد و کلید را از `/proc/<pid>/environ` دور نگه می‌دارد):

<div dir="ltr" align="left">

```sh
( umask 077; openssl rand -base64 32 > /etc/baft-bcc/backup.key )
systemctl edit baft-bcc    # add the two lines below, then save
```

</div>

<div dir="ltr" align="left">

```ini
[Service]
ExecStart=
ExecStart=/usr/local/bin/baft-bcc --listen 127.0.0.1:8080 --state-file /var/lib/baft-bcc/bcc-state.json --admin-token-file /etc/baft-bcc/admin-token --access-file /etc/baft-bcc/access.json --job-key-file /etc/baft-bcc/job-key --backup-dir /var/lib/baft-bcc/backups --backup-key-file /etc/baft-bcc/backup.key
```

</div>

(خط واقعی `ExecStart=` را از `systemctl cat baft-bcc` کپی کنید و پرچم آخر را به آن بیفزایید.) آنگاه BCC در شروع و هر `--backup-interval` (۲۴ ساعت) پشتیبان می‌نویسد و `--backup-daily-retention` برابر ۷ و `--backup-weekly-retention` برابر ۴ را نگه می‌دارد. همین حالا یکی بگیرید و آن را بیرون از میزبان کپی کنید:

<div dir="ltr" align="left">

```sh
curl -fsS -X POST -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" \
  http://127.0.0.1:8080/api/backups/create
ls /var/lib/baft-bcc/backups/
```

</div>

**بازیابی** (آفلاین، BCC باید متوقف باشد؛ قفل state-file این را ثابت می‌کند). روی میزبان پاک‌شده اول BCC را دوباره نصب کنید (بخش ۱)، متوقفش کنید، کلید امانی job، توکن مدیر و فایل دسترسی را برگردانید (وگرنه agentها BCC تازه را رد می‌کنند)، سپس:

<div dir="ltr" align="left">

```sh
systemctl stop baft-bcc
export BAFT_BCC_BACKUP_KEY="$(cat /etc/baft-bcc/backup.key)"
baft-bcc restore-preview --backup /root/manual-XXXX.baftbak --state-file /var/lib/baft-bcc/bcc-state.json
baft-bcc restore --backup /root/manual-XXXX.baftbak --state-file /var/lib/baft-bcc/bcc-state.json
baft-bcc restore --backup /root/manual-XXXX.baftbak --state-file /var/lib/baft-bcc/bcc-state.json --yes
systemctl start baft-bcc
```

</div>

`restore-preview` چیزی را تغییر نمی‌دهد و نشان می‌دهد چه چیزی برمی‌گردد یا ناپدید می‌شود. `restore` بدون `--yes` با کد ۴ خارج می‌شود و چیزی را تغییر نمی‌دهد. کد ۲ مشکل کلید است و کد ۱ رد شدن. کلید اشتباه، یک بیت وارونه در متن رمز، سرآیند ویرایش‌شده، schema پشتیبانی‌نشده، فایل کوتاه‌شده یا خالی همه رد می‌شوند و وضعیت موجود بایت‌به‌بایت دست‌نخورده می‌ماند. بازیابی ابطال‌ها و توکن‌های تازه‌تر را نگه می‌دارد، یک ورودی audit با نام `backup.restore` می‌افزاید و اگر audit فعلیِ غیرخالی لنگر audit پشتیبان را ادامه ندهد رد می‌شود. backup schemaهای ۲ تا ۵ خوانده می‌شوند؛ پشتیبان اضطراری که `baft uninstall` می‌گیرد با `baft-bcc verify-backup --dir DIR` وارسی می‌شود.

پس از شروع، agentها خودشان دوباره وصل می‌شوند؛ با پنل، `GET /api/nodes` و بررسی drift هر تونل تأیید کنید.

## ۶. ارتقا از v0.3.7

۱. روی هر میزبان برنامه را بخوانید: `sudo bash install.sh --plan` (وضعیت `UPGRADE_AVAILABLE`).
۲. **BCC را سرد snapshot بگیرید**: `systemctl stop baft-bcc`، سپس `mkdir -p /root/pre-v040 && cp -p /var/lib/baft-bcc/bcc-state.json* /etc/baft-bcc/* /root/pre-v040/` (و `cp -a /opt/baft/release-state.json /root/pre-v040/`)، باینری‌های v0.3.7 را نگه دارید و `systemctl start baft-bcc`. پیش از تکیه بر snapshot، باینری نگه‌داشتهٔ v0.3.7 را روی یک نسخهٔ آن در پوشهٔ موقت اجرا کنید (LAB بازگشت ارتقای v0.3.7 دقیقاً همین را می‌کند).
۳. BCC را ارتقا دهید (`install.sh --bcc-only --yes`)، سپس هر سرور را (بخش ۴). وضعیت به SQLite schema 16 مهاجرت می‌کند؛ پشتیبان‌های رمزنگاری‌شدهٔ v0.3.7 (schema 2) در v0.4.0 بازیابی می‌شوند.
۴. تونل‌های موجود پیکربندی و کلیدشان را نگه می‌دارند؛ باینری‌های EX/IR بدون جفت‌سازی دوباره جایگزین می‌شوند.
۵. **بازگشت** همان snapshot سرد است، نه downgrade: BCC را متوقف کنید، `rm -f /var/lib/baft-bcc/bcc-state.json*`، snapshot را برگردانید، باینری نگه‌داشتهٔ `baft-bcc` نسخهٔ v0.3.7 را در `/usr/local/bin/baft-bcc` بگذارید (راه نصب‌کننده `--version v0.3.7 --allow-downgrade` است؛ تعویض باینری همان چیزی است که LAB تمرین کرده) و شروع کنید. تغییرات پس از snapshot عمداً از دست می‌روند.

## ۷. محدودیت‌های شناخته‌شده

- حداکثر **۵۰ میلی‌ثانیه** تأخیر اضافه در برقراری اتصال روی پورت ingress برای کلاینت‌هایی که ابتدا چیزی نمی‌فرستند (پروتکل‌هایی که سرور اول حرف می‌زند): پاسخ‌گوی probe منتظر بایت‌های اول می‌ماند.
- Ready شاهد کامل‌شدن عملیات امضاشده به‌علاوهٔ یک رفت‌وبرگشت BCC است، نه اثبات مالکیت یا دسترس‌پذیری از اینترنت (بخش ۳).
- **راه‌اندازی مجدد یا ارتقای agent، ingress عمومی را متوقف می‌کند** (شنونده با فرایند می‌میرد). agent در شروع قاعدهٔ کهنهٔ allow در nft را با handle دقیقش فقط وقتی برمی‌دارد که شواهد کامل socket هسته، فایروال و lease مصرف‌شده باشد؛ ingress فقط پس از آنکه BCC عملیات تازه را آماده و امضا کند برمی‌گردد و رزرو پورت خودکار آزاد نمی‌شود.
- افزودن IR دوم به شنوندهٔ EX در حال اجرا (`baft-pair ex-accept --join` به‌علاوهٔ SIGHUP) **در کد این commit وجود ندارد**، پس این راهنما آن را شرح نمی‌دهد؛ هر تونل شنوندهٔ EX خودش را دارد.
- میزبان IR پس از reboot ingress زنده را adopt نمی‌کند؛ به Apply یا Retire امضاشدهٔ جدید نیاز دارد. تغییرات جزئیِ نامشخص reconciliation می‌خواهند.
- فقط TCP. انتقال UDP نیست. پورت‌های مدیریت و SSH و سرویس‌های نامرتبط هرگز adopt یا متوقف نمی‌شوند.
- مرکز به‌روزرسانی داخل محصول نیست؛ اجرای دوبارهٔ نصب‌کننده راه به‌روزرسانی است. بازگشت به نسخهٔ قدیمی‌تر snapshot می‌خواهد.
- نصب‌کننده هنوز کلید پشتیبان را در unit نمی‌گذارد (drop-in بخش ۵)؛ تا آن را نگذارید پشتیبان‌گیری خاموش است.
- در مقیاس بزرگ در میدان آزموده نشده؛ نتایج LAB و CI ناوگان تولید را توصیف نمی‌کنند.
