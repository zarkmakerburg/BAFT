# BAFT v0.4.0 operations guide

> Persian: [v0.4.0-operations.fa.md](v0.4.0-operations.fa.md)

Status: **development target, not a published release.** v0.4.0 is accepted only by
`scripts/release/accept.sh` at the exact tag SHA (see [the gate](v0.4.0-gate.md) and
[the readiness ledger](v0.4.0-readiness.md)). Every command below was checked against the
code: `install.sh` argument parser, the `baft`, `baft-agent` and `baft-bcc` flag sets, and the
BCC HTTP routes. `go test ./tests/docs -run TestOperationsGuide` fails when this page names a
flag or route that the code does not have. Commands marked "LAB" are exercised by the CI jobs
named in [Evidence](#evidence); nothing here was run on a production fleet.

All commands run as root on a Debian or Ubuntu server (amd64 or arm64). Paths are the installer
defaults: BCC config `/etc/baft-bcc`, BCC state `/var/lib/baft-bcc`, service `baft-bcc`; transport
config `/etc/baft`, state `/var/lib/baft`, service `baft`; agent `/etc/baft-agent`,
`/var/lib/baft-agent`, service `baft-agent`.

## 1. Install

The installer downloads the signed release for the architecture, verifies it against the pinned
root key and the revocation list, and refuses a downgrade or a re-tagged version. Use `--plan`
first: it changes nothing and needs no root and no network.

```sh
curl -fsSLO https://raw.githubusercontent.com/zarkmakerburg/baft/main/install.sh
sudo bash install.sh --plan
```

(Release assets also carry the installer as `baft-install-linux-<arch>`, byte-identical to
`install.sh`; BCC pushes the same file to new servers over SSH.)

**Command Center (BCC), the control plane** (never creates a tunnel):

```sh
sudo bash install.sh --bcc-only
sudo bash install.sh --bcc-only --bcc-domain panel.example.com --bcc-port 8443
```

Without `--bcc-domain` the panel listens on `127.0.0.1:8080` and is reached through an SSH
tunnel or a reverse proxy you run. The installer prints the secret dashboard path and a one-time
password exactly once; a rerun prints `password: not stored`. Rotate it with `sudo baft-panel`.
The admin token is `/etc/baft-bcc/admin-token` (root, 0600) and is used for the HTTP API below.
For SSH enrollment of new servers from the panel, BCC needs `--bcc-public-url https://...`
(plain `http://` only together with `--bcc-allow-insecure-http`).

**A server managed by BCC (agent)**: the agent token comes from `BAFT_AGENT_TOKEN_FILE` and the
BCC job-signing public key from `BAFT_BCC_JOB_KEY`
(`baft-bcc jobkey show --job-key-file /etc/baft-bcc/job-key` on the BCC host):

```sh
sudo env BAFT_AGENT_TOKEN_FILE=/root/agent.token BAFT_BCC_JOB_KEY=PUBLIC_KEY \
  bash install.sh --agent-only --bcc-url https://bcc.example.com --node-id ir-1
```

`--agent-only` also creates the empty `inet baft ingress` nftables chain (see section 3); add
`--no-ingress-chain` to skip it. Offline hosts: `--offline DIR` with an unpacked
`baft-offline-<version>.tar.gz`.

## 2. Pair

### With BCC

Add the server in the panel (SSH enrollment, or the agent install above), then build the tunnel
in the Smart Tunnel Wizard. BCC shows the reviewed plan with its **plan hash**; the tunnel is
created only from that hash, and the nodes apply it as signed jobs with rollback. Nothing reaches
a node unsigned.

### Standalone CLI (BCC unavailable)

Two ways, both without BCC:

1. Classic installer pairing. On the outside server (EX):

   ```sh
   sudo bash install.sh --role ex --public-address EX_IP --ports 443,2053
   ```

   It prints a one-time `BAFTPAIR1:` code (valid 15 minutes, single use). On the Iran server (IR):

   ```sh
   sudo bash install.sh --role ir --pairing-code 'BAFTPAIR1:...'
   ```

   Paste the `BAFTREPLY1:` reply back on the EX (or pass it with `--reply-code`). With
   `--ir-ssh USER@HOST` the EX installs and pairs the IR itself. `--re-pair` deliberately starts
   a new pairing; a rerun never re-pairs on its own.

2. Instance-scoped pairing with `baft tunnel` (this is what the agent calls). Every call needs
   `--instance`, `--metrics-listen` and `--id`:

   ```sh
   baft tunnel ex-code --instance main --metrics-listen 127.0.0.1:9291 --id t1 \
     --address EX_IP --port 443 --target 127.0.0.1:2443 --route-id r1 --output-file /root/ex.code
   baft tunnel ir-apply --instance main --metrics-listen 127.0.0.1:9292 --id t1 \
     --code-file /root/ex.code --route-listen 127.0.0.1:1443 --route-id r1 --output-file /root/ir.reply
   baft tunnel ex-accept --instance main --metrics-listen 127.0.0.1:9291 --id t1 --reply-file /root/ir.reply
   baft tunnel ir-start --instance main --metrics-listen 127.0.0.1:9292 --id t1
   baft tunnel health --instance main --metrics-listen 127.0.0.1:9291 --id t1
   ```

   (`ir-apply` runs on the IR with the EX code copied to a private 0600 file; `rollback` and
   `finalize` complete the lifecycle.) Codes and replies are secrets: use the 0600 files, never
   the command line. Malformed, tampered, expired, replayed or mismatched codes and replies are
   refused and the pending state is kept for a retry.

## 3. Operational public ingress

Public ingress opens a TCP port on the IR host and forwards it into the tunnel route. It is
**default closed**: nothing is opened unless every condition below holds.

On the IR node the agent builds the operational executor only if all hold, otherwise it sends no
capability and ingress jobs are BLOCKED:

- the installed managed-node policy `/etc/baft/ingress/managed-node.json` loads for this
  `--node-id`;
- `<state-dir>/ingress-authority` and `<state-dir>/ingress-journal` are private (0700) and the
  journal chain validates;
- `/usr/sbin/nft` (or `/sbin/nft`) reports exactly one `inet baft ingress` chain
  (`type filter hook input priority -100; policy accept`) with a stable handle. The agent never
  creates the chain: `install.sh --agent-only` does, idempotently, and refuses (exit 3, changes
  nothing) when a chain of that name has another layout.

**Policy bootstrap flag.** The protected policy is created only on request, never implicitly:

```sh
sudo bash install.sh --agent-only --bcc-url https://bcc.example.com --node-id ir-1 --provision-ingress-policy
sudo baft-agent --provision-ingress-policy --node-id ir-1
```

It is a local, root-only command: no BCC contact, no port, no firewall rule, no Apply.

**Flow.** In the Wizard the reviewed plan binds nodes, target, transport, generation, plan hash
and `ConfigPort == Port` (the port in the client config equals the real public port). BCC sends a
signed Apply to the normal enrolled agent. The agent opens the listener and the nftables rule only
under a held, locally verified lease, then reports an authenticated HTTPS receipt (agent to BCC,
certificate-validated, no downgrade). BCC probes the port itself.

**What "Ready" means.** `GET /api/ingress/readiness?tunnel_id=ID` (admin token) returns
`{verified, ready, reason, card}`. It is `Ready` only when all hold: the Apply was dispatched; an
exact authenticated *applied* receipt with verified ownership and complete listener/firewall
evidence exists; and a fresh (at most 5 minutes old) BCC observation agrees on binding, socket
identity, nft chain and rule handles and a TCP payload round trip. Readiness is derived on demand
and never stored, so a restored backup or a stale record cannot carry it; a Retire turns it off.
The deployable client config card (`tunnel_id`, `ir_node`, `config_port`, `public_port`,
`plan_sha256`) is shown only then; it holds no secret.

```sh
curl -fsS -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" \
  "http://127.0.0.1:8080/api/ingress/readiness?tunnel_id=TUNNEL_ID"
```

**Trust model (read this before relying on Ready).** A compromised node agent is out of scope.
BCC's observation reuses the agent's own evidence, so the only independent datum is a nonce echo
that any process holding the port could produce. Ready therefore means "the signed operation
completed and BCC could talk through the port", not "BAFT provably owns the listener" and not
"reachable from the public internet": loopback and namespace LAB results do not certify external
reachability. Test from outside before you hand out a config.

**Release gate.** The `operational ingress v1` workflow must pass at the tag SHA with zero
skipped required tests; `accept.sh` refuses the tag otherwise. See [the gate](v0.4.0-gate.md).

## 4. Update and rollback

Updates are the verified installer rerun; there is no in-product Update Center. A rerun inspects
the host, prints a plan, applies only that plan, verifies it and puts the previous files and
service state back if a check fails. It never rotates keys, overwrites a valid config or re-pairs.

```sh
sudo bash install.sh --plan --json
sudo bash install.sh --role ex --public-address EX_IP --yes
sudo bash install.sh --bcc-only --yes
sudo bash install.sh --version vX.Y.Z --yes
```

Order: BCC first, then the servers, one at a time, checking `baft doctor` and traffic between
steps. BCC can also queue signed update jobs to enrolled agents: `POST /api/deploy` with
`{"node_ids":["ir-1"],"version":"vX.Y.Z"}`.

- A release older than the installed one is refused unless you pass `--allow-downgrade`.
- A release whose binary does not start, or dies as a service, is rolled back automatically.
- Before any change the installer copies each file it will touch to
  `/opt/baft/backups/rerun-<time>/` (newest three kept).
- Downgrading across **SQLite schema 15/16 or backup schema 4/5 needs a verified pre-upgrade
  snapshot** (section 6): a v0.3.7 `baft-bcc` refuses a v0.4.0 state ("newer than this build
  supports") and a v0.4.0 backup ("unsupported backup schema version").

## 4b. Update Center (BCC)

BCC never updates anything by itself. An operator imports a signed release bundle, BCC verifies it
against the pinned release root (revocation list, version floor, re-tag check), shows
installed-versus-latest per server, and an administrator applies a hash-bound plan to **one**
server, which queues the existing signed `update_baft` job. Imports persist (SQLite schema 16,
backup schema 5) and a restore never forgets an import or resurrects an older revocation list.

**The release root pin.** BCC needs a file with the release root public key, started with
`--update-root-pub` (it defaults to `--component-catalog-root`). `install.sh` does **not** pass
this flag to `baft-bcc` today, although the same root key is pinned inside `install.sh`
(`BAFT_PINNED_ROOT_PUB`); until it does, add it with a drop-in (`systemctl edit baft-bcc`, the
same `ExecStart=` reset as in section 5, with `--update-root-pub /etc/baft-bcc/release-root.pub`
appended) and write the file:

```sh
printf '%s\n' 'NJq0LmZ503x67pdXSuNGmSOqaiNJDpYf9nDE8Bwa-JI' > /etc/baft-bcc/release-root.pub
```

Without the pin, `POST /api/updates/import` answers 503 and nothing can be imported. Then:

```sh
scripts/release/update_center_bundle.sh /path/to/unpacked-baft-offline-vX.Y.Z > update-bundle.json
curl -fsS -X POST -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" --data-binary @update-bundle.json \
  http://127.0.0.1:8080/api/updates/import
curl -fsS -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" http://127.0.0.1:8080/api/updates
```

`POST /api/updates/plan` (`node_id`, `kind` = `upgrade` or `rollback`, `target_digest`) returns the
plan with its `plan_hash` and the exact confirmation text; `POST /api/updates/apply` needs the same
fields plus `plan_hash` and `confirmation`. A rollback import additionally needs the header
`X-BAFT-Downgrade-Confirmation: DOWNGRADE <version> <commit>`. The `baft` menu Update item is
read-only guidance.

## 4c. Capability negotiation and boot recovery

**Capability negotiation (set v1).** `HELLO`/`HELLO_ACK` carry `carrier.h2`, `carrier.ws`,
`noise.v1` and `shape.v1`; each side advertises what its config enables, the session uses the
intersection and a missing required capability is refused with a typed reason (no silent
downgrade). Wire-compatible with v0.3.7 in both directions. The optional config key
`transport.require_capabilities` makes a peer lacking a listed capability, **including a v0.3.7
peer**, be refused; during a rolling upgrade leave it unset on both nodes and set it only after
every node runs v0.4.0 (a v0.3.7 config parser rejects the unknown key). See `docs/en/04-protocol-baft1.md`.

**Boot recovery.** `baft-recover.service` (installed and enabled by the installer, ordered before
`sysinit.target`, `baft.service` and the agent; it only orders, never requires) runs
`baft recover boot`, which reconciles an interrupted tunnel change from on-disk evidence and never
starts, stops or restarts a service. Run it by hand to inspect:

```sh
baft recover boot --json
```

A failed or fenced recovery shows in `systemctl --failed` and never blocks the boot.

## 5. Backup and restore

BCC state (nodes, enrollment token hashes, tunnels and plan hashes, jobs, reservations, finance,
the audit hash chain) is backed up as an encrypted file (AES-GCM, authenticated header, backup
schema 5, including Update Center imports). **Not in the backup**: the job-signing key (agents pin it), the admin token, the
access file, the TLS files and the backup key itself. Keep those in escrow separately.

**Enable.** The installer does not write a backup key. Create a private key file and a systemd
drop-in (key file must be a regular file, owner = service user, mode 0600, one link, no symlink;
`--backup-key-file` wins over the `BAFT_BCC_BACKUP_KEY` environment variable and keeps the key
out of `/proc/<pid>/environ`):

```sh
( umask 077; openssl rand -base64 32 > /etc/baft-bcc/backup.key )
systemctl edit baft-bcc    # add the two lines below, then save
```

```ini
[Service]
ExecStart=
ExecStart=/usr/local/bin/baft-bcc --listen 127.0.0.1:8080 --state-file /var/lib/baft-bcc/bcc-state.json --admin-token-file /etc/baft-bcc/admin-token --access-file /etc/baft-bcc/access.json --job-key-file /etc/baft-bcc/job-key --backup-dir /var/lib/baft-bcc/backups --backup-key-file /etc/baft-bcc/backup.key
```

(Copy the real `ExecStart=` line from `systemctl cat baft-bcc` and append the last flag.) BCC then
writes a backup at start and every `--backup-interval` (24h), keeping `--backup-daily-retention` 7
and `--backup-weekly-retention` 4. Take one now, and copy it off the host:

```sh
curl -fsS -X POST -H "Authorization: Bearer $(cat /etc/baft-bcc/admin-token)" \
  http://127.0.0.1:8080/api/backups/create
ls /var/lib/baft-bcc/backups/
```

**Restore** (offline, BCC must be stopped; the state-file lock proves it). On a wiped host install
BCC again first (section 1), stop it, put the escrowed job key, admin token and access file back
(otherwise agents reject the new BCC), then:

```sh
systemctl stop baft-bcc
export BAFT_BCC_BACKUP_KEY="$(cat /etc/baft-bcc/backup.key)"
baft-bcc restore-preview --backup /root/manual-XXXX.baftbak --state-file /var/lib/baft-bcc/bcc-state.json
baft-bcc restore --backup /root/manual-XXXX.baftbak --state-file /var/lib/baft-bcc/bcc-state.json
baft-bcc restore --backup /root/manual-XXXX.baftbak --state-file /var/lib/baft-bcc/bcc-state.json --yes
systemctl start baft-bcc
```

`restore-preview` changes nothing and shows what would come back or disappear. `restore` without
`--yes` exits 4 and changes nothing. Exit 2 is a key problem, 1 a refusal. A wrong key, a flipped
bit in the ciphertext, an edited header, an unsupported schema, a truncated or empty file are all
refused, and the existing state stays byte-identical. A restore keeps newer revocations and
tokens, appends one `backup.restore` audit entry and is refused when a non-empty current audit
does not extend the backup's audit anchor. Backup schemas 2 to 5 are readable; the emergency
backup `baft uninstall` takes is checked with `baft-bcc verify-backup --dir DIR`.

After the start, agents reconnect by themselves; confirm with the panel, `GET /api/nodes` and a
drift check of each tunnel.

## 6. Upgrade from v0.3.7

1. Read the plan on every host: `sudo bash install.sh --plan` (state `UPGRADE_AVAILABLE`).
2. **Snapshot BCC cold**: `systemctl stop baft-bcc`, then
   `mkdir -p /root/pre-v040 && cp -p /var/lib/baft-bcc/bcc-state.json* /etc/baft-bcc/* /root/pre-v040/`
   (and `cp -a /opt/baft/release-state.json /root/pre-v040/`), keep the v0.3.7 binaries and
   `systemctl start baft-bcc`. Before you rely on the snapshot, start the retained v0.3.7 binary
   against a copy of it in a scratch directory (the v0.3.7 upgrade-rollback LAB does exactly this).
3. Upgrade BCC (`install.sh --bcc-only --yes`), then each server (section 4). The state migrates
   forward to SQLite schema 16; v0.3.7 encrypted backups (schema 2) restore into v0.4.0.
4. Existing tunnels keep their config and keys; EX/IR binaries are replaced without re-pairing.
5. **Rollback** is the cold snapshot, not a downgrade: stop BCC, `rm -f /var/lib/baft-bcc/bcc-state.json*`,
   copy the snapshot back, put the retained v0.3.7 `baft-bcc` binary back at
   `/usr/local/bin/baft-bcc` (the installer's route is `--version v0.3.7 --allow-downgrade`; the
   binary swap is what the LAB drill exercised), start. Changes made after the snapshot are lost
   by design.

## 7. Known limits

- **50 ms** of added connection latency, at most, on an ingress port for clients that send
  nothing first (server-speaks-first protocols): the probe responder waits for first bytes.
- Ready is evidence of a completed signed operation plus a BCC round trip, not proof of ownership
  or of internet reachability (section 3).
- **A BAFT agent restart or upgrade stops public ingress** (the listener dies with the process). At start the agent removes the stale nft allow rule by its exact handle only when kernel socket, firewall and consumed-lease evidence is complete; ingress returns only after BCC stages and signs a new operation, and the port reservation is not released automatically.
- Joining a second IR to an already running EX listener (`baft-pair ex-accept --join` plus SIGHUP) is **not present in the code at this commit**, so this guide does not document it; each tunnel gets its own EX listener.
- A rebooted IR host does not adopt a live ingress; it needs a new signed Apply or Retire.
  Uncertain partial changes need reconciliation.
- TCP only. No UDP transports. Management and SSH ports and unrelated services are never adopted
  or stopped.
- No in-product Update Center; the installer rerun is the update path. Downgrade needs a snapshot.
- The installer does not yet wire a backup key into the unit (section 5 drop-in); backups are off
  until you do.
- Not field-proven at scale; LAB and CI results do not describe a production fleet.
