# v0.4.0 operations guide

What an operator does to install, pair, run, update, back up and recover a
v0.4.0 deployment. Everyday steps live in the user guide
([English](../en/guide/README.md), [Persian](../fa/guide/README.md)); this page
covers what v0.4.0 adds or changes and points to the detailed pages. Limits are
in [KNOWN-LIMITATIONS.en.md](../../KNOWN-LIMITATIONS.en.md).

## 1. Install and pair

Unchanged from the guide: [Install](../en/guide/01-install.md).

```bash
sudo bash install.sh --role ex --public-address HOST_OR_IP
sudo bash install.sh --role ir --pairing-code BAFTPAIR1:...
sudo bash install.sh --plan            # inspect, change nothing
```

New in v0.4.0:

- The installer also installs `baft-recover.service`, which runs
  `baft recover boot` once at boot to finish or roll back tunnel changes that a
  crash or power loss interrupted. It is ordered after local filesystems and
  never pairs, re-keys or touches foreign files.
- `--agent-only` (BCC-managed servers) creates the pinned, empty
  `inet baft ingress` nftables chain. A different existing layout is refused;
  foreign nft objects are never touched. `--no-ingress-chain` skips it.
  `--provision-ingress-policy` additionally runs the local root-only policy
  bootstrap (off by default; it does not by itself enable public ingress).

## 2. Several IRs on one EX listener (shared multiplexing)

One EX listener, port and process can serve several IR tenants, each with its
own identity and target, without restarting live flows:

```bash
baft-pair ex-accept ... --join /etc/baft/baft.yaml   # add this IR as a tenant
systemctl reload baft                                 # SIGHUP: apply live
```

`limits.max_flows_per_peer` caps how many flows one tenant may hold. Design and
current gaps: [shared-multiplexing.md](../design/shared-multiplexing.md). A
shared-listener instance is not yet created through the tunnel transaction and
systemd instance path; `--join` is the supported route.

## 3. Public ingress (BCC-managed)

Public ingress is **default-closed**. BCC enqueues a signed Apply or Retire job
only for an enrolled node whose agent sends a fresh heartbeat advertising the
`operational-ingress-v1` capability. The node accepts the job only with a
verified signature, a held lease and the installed policy pin, and the Wizard
shows the config card only after an authenticated receipt and an independent
probe of the public port.

After an agent restart:

```bash
baft-agent --ingress-reconcile auto     # default: finish only with full evidence
baft-agent --ingress-reconcile report   # evaluate and print, change nothing
baft-agent --reconcile-ingress          # one-shot: print evidence and exit
```

`auto` removes only what kernel, firewall and authority evidence proves is
ours; anything uncertain stays fenced and is reported.

## 4. Update

Servers: rerun the installer (anti-downgrade, plan first, automatic rollback):
[Update, backup and uninstall](../en/guide/05-update-backup-uninstall.md).

BCC Update Center ([design](../design/update-center.md)):

- Import a signed release made by
  `scripts/release/update_center_bundle.sh <unpacked offline bundle>`.
- Review the per-node plan, then apply with the typed confirmation
  `UPDATE <node> <version>`. Upgrade uses the existing signed `update_baft`
  job; rollback is always the verified installer run on the node.
- Imports need a pinned release root: start `baft-bcc` with
  `--update-root-pub FILE` (or `--component-catalog-root FILE`). **The BCC unit
  written by `install.sh` passes neither, so on an installed panel imports
  answer 503 (no root pinned) until the operator adds one.** Mirror fetch is
  not implemented; import is manual.

## 5. Backup and restore

BCC: [backups and restore](../en/29-bcc-backup-restore-preview.md).

```bash
baft-bcc restore-preview --backup FILE --state-file STATE   # read-only
baft-bcc restore --backup FILE --state-file STATE --yes     # BCC stopped
```

Scheduled encrypted backups run only when a backup key is configured
(`--backup-key-file`, preferred, or `BAFT_BCC_BACKUP_KEY`). **The BCC unit
written by `install.sh` sets `--backup-dir` but no key, so no scheduled backup
is written until the operator configures one.** Keep the key off the BCC host's
backup directory.

Servers: `/etc/baft` holds config, keys and certificates; a standard uninstall
keeps it. The installer copies files it changes to
`/opt/baft/backups/rerun-<time>/`.

## 6. Diagnose

```bash
baft status --json
baft doctor --preview-fixes
baft logs -n 200
baft support-bundle --out baft-support.tar.gz   # secret-safe
```

## 7. Upgrade from v0.3.7

Pair once, then rerun the installer on both peers. v0.3.7 peers keep working:
the HELLO capability exchange falls back to the frozen v0.3.7 wire format, and
both v0.3.7 LAB workflows (`gamma-v037-upgrade-lab`,
`gamma-v037-tunnel-upgrade-lab`) cover binary replacement without re-pairing.
Downgrade rules for the BCC database and backups are in
[KNOWN-LIMITATIONS.en.md](../../KNOWN-LIMITATIONS.en.md).
