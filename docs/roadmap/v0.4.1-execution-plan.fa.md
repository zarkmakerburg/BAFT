8. محیط LAB مجاز است؛ نتایج شبیه‌سازی‌شده باید از آزمایش واقعی Node/Kernel/Network تفکیک شوند.

## 2. هدف محصول و محدوده نسخه

هدف v0.4.1 تکمیل تجربه «ساخت و مدیریت اتصال امن بین دو Node» در BCC است؛ کاربر باید بتواند Node مبدأ، Node مقصد، مقصد سرویس و پورت عمومی را مشخص کند، یک Review روشن ببیند و با یک Deploy کنترل‌شده تونل سالم بسازد.

### خروجی مورد انتظار

- Public Ingress واقعی روی Node ایران، با مالکیت، رزرو پایدار، Firewall محدود، Health Check و Rollback.
- استفاده مجدد امن از Shared Inter-Node Transport فقط وقتی قابلیت واقعی multiplex و جداسازی tenant اثبات شده باشد.
- fallback شفاف به Dedicated Listener در صورت نبود قابلیت Shared Multiplex یا اشغال/ناسازگاری پورت.
- Wizard ساده و قابل فهم؛ تنظیمات فنی در Advanced باقی بمانند.
- تشخیص مسیر و پیشنهاد Direct/Reverse بر اساس شواهد تازه و قابلیت‌های واقعی Agentها.
- حفظ سرویس‌های موجود، به‌خصوص listener قدیمی پورت 2053 و همه منابع غیرمتعلق به BAFT.
- نصب، Pairing، Upgrade، Rollback، Restart و Uninstall قابل پیش‌بینی و مستند.
- پنل واحد BCC برای مدیریت، تست، وضعیت، عیب‌یابی و تاریخچه.

### خارج از محدوده P0

موارد زیر تا زمانی که نیاز محصولی و پذیرش مستقل نداشته باشند، نباید مسیر انتشار v0.4.1 را متوقف یا پیچیده کنند:

- پیاده‌سازی تمام 28 روش ادعاشده در C-BAFT.
- GRE/IPIP/VXLAN/GENEVE به‌عنوان قابلیت عمومی پیش‌فرض.
- FEC تطبیقی و Multi-Lane پیشرفته.
- ادعای سازگاری کامل استاندارد QUIC یا DTLS برای قالب‌های شبیه‌سازی‌شده.
- تغییر یا مدیریت UUID، کاربران، لینک اشتراک یا Subscriptionهای 3X-UI.
- تضمین ضدسانسور بودن صرفاً به‌دلیل استفاده از TCP/443.
- تغییر تنظیمات سرورهای عملیاتی یا Deploy خودکار خارج از LAB.

## 4. معماری و اصول غیرقابل مذاکره

### 4.1 مرز مسئولیت

- **BCC:** مرجع تصمیم، سیاست، انتخاب Node/مسیر، ساخت plan، review و صدور Job.
- **Agent:** اجرای Job معتبر، امضاشده، مجاز، منقضی‌نشده و ضد Replay.
- **Journal:** ثبت durable مراحل، شناسه عملیات، منابع قبل/بعد، نتیجه و checkpoint بازیابی.
- **Ingress Manager:** رزرو و مدیریت listener عمومی IR و firewall ruleهای scoped.
- **Transport Runtime:** listener/carrier و sessionهای احرازشده؛ بدون اختیار مستقل صدور مجوز.
- **Route/Target Manager:** نگاشت هویت احراز‌شده و route به مقصد ثابت و مجاز.
- **Health/Probe:** سنجش کیفیت و ارائه evidence زمان‌دار؛ حق اعمال تغییر ندارد.
- **Wizard:** تبدیل انتخاب کاربر به plan معتبر؛ render و preflight نباید اثر جانبی میزبان ایجاد کنند.
- **Installer:** نصب نسخه معتبر، Pairing، سرویس‌ها، به‌روزرسانی و بازیابی.

### 4.2 قواعد امنیتی

1. هیچ ورودی UI، فیلد JSON یا شناسه route به‌تنهایی مجوز نیست.
2. هر عملیات میزبان باید به هویت Node، Job، plan hash، generation و مالکیت منابع bind شود.
3. قبل از حذف/تغییر Interface، Route، Listener، Firewall یا sysctl باید مالکیت و وضعیت قبلی اثبات شود.
4. Firewall cleanup بر اساس نام یا comment به‌تنهایی مجاز نیست.
5. مقدار قبلی sysctl و منابع سیستم باید پیش از تغییر durable ثبت و در rollback بازیابی شود.
6. هیچ Driver حق bypass کردن BCC authorization یا Agent guard را ندارد.
7. هیچ خطای اجرا یا receipt گم‌شده نباید به موفقیت جعلی، آزادسازی رزرو بدون اثبات یا حذف منابع sibling منجر شود.
8. عملیات باید idempotent و در برابر تکرار، crash و اجرای هم‌زمان مقاوم باشند.
9. Secretها نباید در log، URL قابل اشتراک یا telemetry ظاهر شوند.
10. هیچ downgrade امنیتی یا انتخاب transport بدون capability/evidence معتبر مجاز نیست.

### 4.3 چرخه عمر تغییر

هر تغییر میزبان باید این مراحل را طی کند:

`Validate → Prepare → PersistIntent → Apply → Verify → Commit`

در شکست:

`DetectFailure → ReconcileObservedState → RollbackOwnedEffects → VerifyRestoration → RecordOutcome`

- «ارسال دستور» معادل Apply موفق نیست.
- «Apply برگشت بدون خطا» به‌تنهایی معادل سرویس سالم نیست.
- «listener حاضر است» به‌تنهایی تحویل داده تا مقصد را اثبات نمی‌کند.
- «receipt دریافت شد» باید با هویت، operation، generation و وضعیت واقعی effect تطبیق کند.
- در حالت نامشخص، وضعیت باید Unknown/Needs reconciliation بماند؛ هرگز Ready اعلام نشود.

## 5. قابلیت‌های منتخب C-BAFT و نحوه اقتباس

C-BAFT یک محصول مستقل مشتق از CIAUB/C-Tunnel است، نه شاخه‌ای از BAFT. فقط ایده‌ها و قابلیت‌هایی که با مدل امنیتی BAFT سازگارند اقتباس می‌شوند.

| قابلیت/ایده C-BAFT | ارزش برای BAFT | نحوه اقتباس |
|---|---|---|
| Connection Test | تشخیص سریع مسیر و علت شکست | توسعه در BCC بر اساس Agent capability و path evidence امضاشده/احرازشده |
| Direct/Reverse comparison | انتخاب مسیر مناسب | استفاده از probeهای موجود و Auto-Select؛ بدون تصمیم بر اساس Ping تنها |
| Best Direct/Reverse UX | حذف اصطلاحات پیچیده از مسیر ساده | نمایش پیشنهاد، دلیل، evidence age و گزینه جایگزین |
| Capability Catalog | شناخت روش‌های قابل اجرا | catalog مبتنی بر binary نصب‌شده و capability واقعی هر دو Node |
| Traffic/Health overview | مشاهده کیفیت و مصرف | اتصال به telemetry واقعی BAFT با freshness و provenance |
| Advanced settings separation | حفظ قدرت برای مدیر حرفه‌ای | Simple/Advanced؛ تنظیمات خطرناک با توضیح و validation |
| Import/share workflow concepts | ساده‌کردن Pairing | فقط در صورت حفظ one-time token، expiry، identity binding و عدم افشای secret |

### موارد ممنوع برای کپی مستقیم

- پنل یا Backend مستقل C-BAFT به‌عنوان control plane دوم.
- اسکریپت kernel cleanup که Interface را صرفاً بر اساس نام حذف می‌کند.
- Firewall cleanup صرفاً مبتنی بر comment tag.
- تغییر ip_forward بدون restore مقدار قبلی.
- Panel مدیریتی عمومی روی HTTP.
- SHA-256 سریع به‌عنوان KDF برای passphrase انسانی.
- اجرای اسکریپت mutable شاخه main با root بدون pinning و تأیید اصالت.
- نصب غیرتراکنشی بدون backup و rollback.
- وابستگی اجباری WireGuard برای Transportهایی که به آن نیاز ندارند.
- معرفی packet look-alike به‌عنوان interoperability واقعی QUIC/DTLS.

## 6. برنامه اجرایی مرحله‌ای

ترتیب زیر dependency-aware است. کارهای مستقل می‌توانند موازی شوند، اما هیچ مرحله‌ای نباید پیش‌نیاز امنیتی یا lifecycle مرحله قبلی را دور بزند.

### Stage 0 — Baseline و جلوگیری از دوباره‌کاری

**اولویت: P0 | خروجی: baseline قابل بازتولید**

- main، tag، release، شاخه‌ها، PRها و Issue #269/#67 را دوباره بخوان.
- head و workflow دقیق #292/#293/#294 و وابستگی‌هایشان را ثبت کن.
- فایل‌های مرتبط BCC/Agent/Journal/Ingress/Firewall/Wizard/Installer را map کن.
- برای هر قابلیت #269، وضعیت را به یکی از این حالت‌ها دسته‌بندی کن: Implemented+Verified، Implemented+Unverified، Partial، Missing، Blocked.
- تست‌های موجود را با نام، command، محیط، SHA و محدودیت ثبت کن.
- هر قابلیت موجود را قبل از نوشتن مجدد با تست یا code path اثبات کن.

**قبولی:** جدول Gap با مسیر کد، تست، SHA و شاهد؛ بدون ادعای سبز بر اساس نتایج قدیمی.

### Stage 1 — بستن lifecycle و recoveryهای باز

**اولویت: P0 | وابستگی: Stage 0**

- PR #292: بررسی نهایی reservation generation، tombstone identity، lifecycle cleanup و تست crash boundaries.
- PR #293: بررسی دقیق retry پس از Retire و receipt failure، replay، identity drift و host cleanup.
- PR #294: بررسی shutdown join، cancellation، hijacked socket، session cleanup و cross-tenant denial.
- خطای ECONNRESET مورد انتظار denial باید در تست به‌شکل دقیق و محدود تفسیر شود؛ پذیرش reset عمومی یا صفر داده بدون route-correlated proof مجاز نیست.
- cold-start، systemd process death، restart واقعی Agent و بازیابی پس از reboot جداگانه تست شوند.
- برای هر PR، تست‌های خودش و تست کامل لازم روی head نهایی اجرا شوند؛ نتیجه branch parent جایگزین نیست.

**قبولی:** هیچ leak یا false success در shutdown/retry/replay نباشد؛ cleanup فقط منابع متعلق را تغییر دهد؛ نتیجه hosted و local جدا گزارش شوند.

### Stage 2 — حل failed-Apply و reservation reconciliation در BCC

**اولویت: P0 | گیت اصلی #269**

- مسیر BCC را از plan review تا signed job، Agent Apply، receipt، timeout و reconciliation دنبال کن.
- حالت‌های crash قبل از Apply، حین Apply، بعد از effect و قبل از receipt را مدل کن.
- بعد از Apply ناموفق یا receipt مفقود، BCC نباید reservation را بدون مشاهده و اثبات آزاد کند.
- reconciliation باید وضعیت واقعی host را از طریق evidence تازه و identity-bound بخواند.
- آزادسازی پورت فقط بعد از اثبات absence همه listenerها، ruleها، sessionها و effectهای مربوط به همان generation مجاز است.
- generation و tombstone باید مانع replay و acknowledgement قدیمی شوند.
- failure باید قابل retry باشد، بدون ایجاد listener/firewall اضافی یا حذف sibling.
- testهای دو writer، crash در مرزهای durable، retry پس از receipt failure و restart store الزامی‌اند.

**قبولی:** هر transition در BCC با observed state قابل توضیح باشد؛ هیچ رزرو نامعتبر آزاد یا binding آزادشده دوباره زنده اعلام نشود.

### Stage 3 — Shared Inter-Node Transport واقعی

**اولویت: P0 | بعد از اثبات lifecycle و identity**

ابتدا ADR کوتاه و دقیق بنویس و سپس implementation را ادامه بده.

- بررسی کن listener موجود چه session/carrierای را میزبانی می‌کند و tenant identity از کجا اثبات می‌شود.
- یک tenant باید identity مستقل و session مستقل داشته باشد؛ اشتراک یک session یا کلید بین tenantها ممنوع است مگر پروتکل جداگانه با تحلیل تهدید و پذیرش مستقل.
- route lookup باید با `(authenticated peer identity, route ID)` انجام شود.
- route ID namespace باید tenant-scoped شود؛ target فقط از config سمت EX تعیین شود.
- سقف flow و منابع per-tenant تعریف شود تا یک tenant نتواند منابع مشترک را مصرف کند.
- اضافه/حذف tenant نباید sessionهای tenantهای دیگر را قطع کند.
- tenant removal باید ابتدا admission/auth را ببندد و سپس فقط session و flowهای همان tenant را drain/cancel کند.
- تغییر config باید atomic و validate-before-publish باشد.
- compatibility و negotiation باید explicit باشد؛ capability `multiplex-v1` فقط زمانی advertise شود که هر دو peer و runtime واقعاً آن را پیاده و قبول کرده باشند.
- اگر capability کامل نیست، Auto-Select باید Dedicated Listener را انتخاب کند یا با دلیل روشن fail-closed شود.
- TCP/443 فقط یک port candidate است؛ نه proof از availability و نه تضمین censorship resistance.

**قبولی:** دو یا چند tenant هم‌زمان ترافیک واقعی مستقل داشته باشند؛ حذف/خرابی یک tenant به دیگری آسیب نزند؛ quotas، route isolation، concurrent streams، restart، rollback و -race تست شوند؛ wire compatibility با نسخه‌های قبلی مستند باشد.

### Stage 4 — Public Ingress روی IR و Firewall

**اولویت: P0 | وابستگی: Stage 2 و قراردادهای Stage 3**

- public client port پیش‌فرض از EX application target port گرفته شود؛ این مقدار باید availability/ownership check شود.
- چهار پورت از هم تفکیک شوند: public IR ingress، IR local route listener، EX outer transport listener، EX application target.
- subscription domain در BCC اضافه نشود؛ 3X-UI مالک user/UUID/subscription باقی می‌ماند.
- اگر public port با target port فرق دارد، الزام rewrite بیرونی Custom Share Address/port واضح و blocking نمایش داده شود.
- IR listener باید به local ingress همان tunnel bind شود.
- firewall rule باید scoped و ownership-bound باشد.
- reboot persistence و startup order باید اثبات شود.
- target reachability از EX جداگانه بررسی شود.
- Existing 2053 Imperial Crown و هر سرویس نامرتبط باید حفظ شود.
- edit/delete/retire باید sibling tunnelها و shared listener را تا آخرین owner حفظ کنند.
- Deploy باید transactional باشد و partial failure را به rollback قابل اثبات ببرد.

**قبولی:** مسیر واقعی client → public IR port → BAFT ingress → authenticated inter-node transport → EX route → target TCP service با payload/checksum اثبات شود؛ conflict و partial failure بدون آسیب به سرویس‌های موجود مدیریت شوند.

### Stage 5 — Auto-Select و Connection Diagnostics

**اولویت: P0 برای پایه موجود، P1 برای تحلیل‌های اضافه**

- از `docs/design/auto-select.md` و endpoint/testهای موجود شروع کن؛ کد موازی نساز.
- capability هر دو Node باید از binary نصب‌شده و report احرازشده بیاید.
- path evidence باید تازه، کامل، برای همان pair/address family/port و دارای probe ID/time باشد.
- CONNECT_ONLY یا HANDSHAKE_ONLY نباید به FULL_DATA تبدیل شوند.
- تصمیم باید بر اساس policy hard constraints، FULL_DATA، stability/trickle، loss، RTT، port ownership و capability باشد.
- هیچ auto-selection در render صفحه یا بدون action صریح نباید host mutation ایجاد کند.
- reviewed plan باید candidateهای انتخاب/ردشده، evidence age، port mapping، exact effects و rollback را hash کند.
- هنگام Deploy تمام evidence و ownership دوباره validate شود.
- دلیل رد هر گزینه به زبان ساده نمایش داده شود.

**اقتباس C-BAFT:** UX مقایسه Direct/Reverse و گزارش تست؛ نه منطق ranker مستقل یا انتخاب بر اساس Ping تنها.

**قبولی:** سناریوهای stale evidence، capability drift، port conflict، loss، handshake-only، changed plan hash و no-candidate fail-closed باشند.

### Stage 6 — BCC Wizard و پنل واحد

**اولویت: P0**

مسیر Simple:

1. انتخاب Node داخل و خارج.
2. انتخاب سرویس مقصد و target port.
3. پیشنهاد public client port با default صحیح.
4. اجرای Preflight فقط با درخواست کاربر.
5. نمایش Review شامل تغییرات، ریسک، سرویس‌های حفظ‌شده و روش اتصال.
6. Deploy با یک اقدام روشن.
7. نمایش progress و نتیجه واقعی Verify.
8. نمایش راهکار خطا و retry امن.

Advanced:
- Dedicated/Shared transport فقط بر اساس capability واقعی.
- Direct/Reverse و carrier سازگار.
- تنظیمات مجاز MTU و tuning موجود.
- جزئیات probe، evidence age و rejection reason.
- هیچ تنظیمی نباید authorization یا ownership را override کند.

صفحات اصلی:
- Overview و سلامت کلی.
- Nodes و نسخه Agent.
- Tunnels و lifecycle.
- Connection Test / path comparison.
- Health / traffic / latency / loss.
- Operations / Journal / recovery history.
- Security / identity / pairing.
- Updates / backup / rollback.
- Settings.

UX الزامی:
- فارسی RTL و انگلیسی LTR.
- دسکتاپ و موبایل واقعی.
- وضعیت Unknown از Disconnected و Healthy تفکیک شود.
- داده telemetry همراه timestamp/freshness باشد.
- پیام کاربرپسند همراه remediation؛ جزئیات فنی در expandable detail.
- confirmation برای عملیات مخرب/تغییر Firewall.
- operation ID برای پشتیبانی و گزارش.
- دسترس‌پذیری، keyboard navigation و validation فرم.
- no silent success و no stale status.

**قبولی:** browser E2E در FA/EN، RTL/LTR و viewport موبایل؛ تست keyboard/accessibility پایه؛ مسیر کامل از انتخاب Node تا اتصال و delete/edit.

### Stage 7 — Installer، Pairing، Upgrade، Recovery و Uninstall

**اولویت: P0**

نصب:
- تشخیص distro/version/arch/kernel/systemd و نیازمندی‌ها.
- dependency فقط بر اساس Driver و role انتخاب‌شده.
- دانلود نسخه pin شده از release.
- verify امضا و root/revocation و manifest پیش از اجرای binary.
- plan قبل از mutation و backup از فایل‌ها و تنظیمات.
- نصب اتمیک و transactional همه اجزای مرتبط، نه فقط mv تک‌فایل.
- ساخت/Pairing هویت Node با token کوتاه‌عمر و یک‌بارمصرف.
- systemd hardening متناسب با قابلیت‌های واقعی سرویس.
- health check و ثبت نسخه/هویت در BCC.

Upgrade:
- compatibility check بین BCC/Agent/Driver/schema.
- backup و migration versioned.
- نصب و restart کنترل‌شده.
- health check و verify عملکرد.
- rollback خودکار در شکست.
- جلوگیری از downgrade ناامن.

Recovery/Uninstall:
- حفظ داده و secretها طبق سیاست کاربر.
- پاک‌سازی فقط منابع اثبات‌شده متعلق به BAFT.
- restore sysctl/firewall/routes به مقدار قبلی.
- باقی‌گذاشتن منابع مبهم و گزارش دقیق به‌جای حذف حدسی.
- تست واقعی systemd stop/start، process kill، reboot و rollback.

**قبولی:** installer fault-injection، online/offline install، upgrade از نسخه قبلی، rollback، restart و uninstall روی distro/archهای اعلام‌شده؛ هیچ ادعای پشتیبانی خارج از ماتریس آزمون‌شده.

### Stage 8 — اقتباس محدود قابلیت‌های تکمیلی C-BAFT

**اولویت: P1؛ فقط بعد از P0**

- نمایش traffic و per-tunnel throughput با منبع و timestamp.
- نمودار RTT/Jitter/Loss و trend.
- connection test قابل تکرار و export گزارش.
- catalog قابلیت‌ها و dependencyهای هر transport.
- MTU discovery فقط اگر probe معتبر و rollback موجود باشد.
- FEC یا Multi-Lane فقط با benchmark واقعی و اثر مثبت قابل تکرار.
- L2/L3 drivers فقط با use case، threat model، lifecycle و مالکیت مستقل.
- هیچ transportی بدون encryption/authentication contract روشن در مسیر حساس انتخاب خودکار نمی‌شود.

### Stage 9 — LAB و آزمون انتشار

**اولویت: P0**

- ابتدا تست‌های deterministic و containerized.
- سپس Linux namespace/kernel/nft/systemd واقعی در runner دارای capability.
- سپس ماتریس شش Node: دو Node ایران و چهار Node خارجی در مناطق مختلف، اگر زیرساخت و دسترسی فراهم باشد.
- برای هر Node نسخه OS/kernel، region، CPU/RAM، مسیر و محدودیت ثبت شود.
- latency/loss/jitter مصنوعی جدا از نتایج اینترنت واقعی برچسب بخورد.
- زوج‌های IR↔EX و جهت‌های Direct/Reverse طبق ماتریس انتخاب شوند.
- shared listener چند tenant، sibling preservation، failure injection، restart و rollback سنجیده شوند.
- هیچ آزمایش واقعی روی سرور production بدون مجوز مشخص انجام نشود.

### Stage 10 — Release readiness

- تکمیل CHANGELOG فارسی/انگلیسی.
- به‌روزرسانی docs نصب، wizard، transport، troubleshooting، upgrade و rollback.
- ساخت release artifacts از exact commit.
- SBOM/provenance و manifest طبق pipeline پروژه.
- امضای مستقل و verify عمومی؛ کلید خصوصی هرگز وارد محیط عامل/CI نشود.
- اجرای release acceptance از assetهای منتشرشده.
- گزارش محدودیت‌های باقی‌مانده و ماتریس پشتیبانی.
- انتشار فقط بعد از GO gate همان SHA.

## 7. ماتریس آزمون اجباری

| حوزه | آزمون‌های لازم |
|---|---|
| Reservation | duplicate, stale generation, released tombstone, concurrent writers |
| Crash | قبل/حین/بعد Apply، بعد commit و قبل receipt |
| Identity | wrong peer, revoked peer, key drift, replayed job |
| Ingress | bind conflict, target unreachable, client payload end-to-end |
| Firewall | foreign rule preservation, exact owner cleanup, prior sysctl restore |
| Shared listener | 2+ tenant، concurrent flow، tenant add/remove، sibling continuity |
| Isolation | cross-tenant route denial، zero payload delivery، valid peer success |
| Auto-select | stale/missing evidence، capability drift، loss، RTT، port conflict |
| Shutdown | idle/active flow، WS/H2 cancellation، process exit، goroutine join |
| Restart | Agent restart، systemd restart، host reboot، durable recovery |
| Installer | fresh install، repeat install، missing dependency، interrupted install |
| Upgrade | compatible، incompatible، migration failure، rollback |
| UI | FA/EN، RTL/LTR، desktop/mobile، keyboard، stale/unknown status |
| Security | authorization، CSRF/session، secret redaction، signature/revocation |
| Load | concurrent tunnels، backpressure، per-tenant quota، long soak |
| Release | exact-SHA CI، artifact provenance، signature verify، public acceptance |

برای هر آزمون باید command، environment، exact SHA، expected result، actual result، exit code، artifact/log و محدودیت‌ها ذخیره شوند. SKIP فقط وقتی قابل قبول است که دلیل، دامنه و جایگزین معتبر آن مشخص باشد؛ صفر-SKIP برای gateهایی که صراحتاً الزام شده‌اند اجباری است.

## Appendix A — تصمیم محصول درباره C-BAFT

BAFT قرار نیست C-BAFT را در خود کپی کند یا به فهرست 28 پروتکل آن برسد. مزیت رقابتی BAFT باید «اتصال امن، مدیریت‌شده، قابل مشاهده و قابل بازیابی» باشد. ارزشمندترین بخش‌های C-BAFT برای این هدف، تجربه تست اتصال، مقایسه Direct/Reverse، capability catalog، نمایش سلامت و جداکردن تنظیمات پیشرفته‌اند. این‌ها باید داخل BCC و روی API/Agent/Journal خود BAFT پیاده شوند.

## Appendix B — ادعاهای ممنوع در گزارش

- «CI سبز است» بدون ذکر exact SHA و workflow.
- «تونل سالم است» بدون تست payload تا مقصد.

- «Rollback موفق است» بدون بررسی وضعیت واقعی منابع بعد از rollback.
